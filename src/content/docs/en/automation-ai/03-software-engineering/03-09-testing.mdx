## Why this matters

You change a formula, and the report looks fine. Two months later, someone notices that a
total has been wrong since the change. A **test** is a small program that checks that
another piece of code gives the right answer. It runs in seconds and catches the kind of
mistake that you would not see by eye.

Tests matter even more when an assistant writes code. They let you check the work
without reading every line as an expert.

<CaseStudy>
	Daniela writes a function that totals sale amounts. A test says: for these
	three amounts, the total must be exactly 5100.00. If a later change gets it
	wrong by a cent, the test fails at once.
</CaseStudy>

## The idea

A test has three parts:

1. **Set up** some known input.
2. **Run** the code.
3. **Check** the result against the answer you worked out by hand.

## Reading a pytest test

**pytest** is the tool the course uses to run tests. First, the code under test:

<Example file="part03/09_totals.py" />

The function `total_amount` takes amounts written as text and adds them exactly, using
`Decimal` from lesson 1.8. Now the tests:

<Example file="part03/test_09_totals.py" />

Read them:

- A test is a function whose name starts with `test_`. pytest finds these itself.
- `assert` means "this must be true". If it is false, the test fails.
- `test_total_of_three_sales` says the total of 2200.00, 1500, and 1400.00 is exactly 5100.00.
- `test_total_of_nothing_is_zero` checks an edge case: an empty list.
- `test_cents_are_exact` checks that 0.10 plus 0.20 is exactly 0.30, the float problem
  from lesson 1.8.

The long lines at the top only load the file under test. Part 4 explains how that
works normally.

When you run pytest, it prints a dot for each test that passes and a detailed message for
each that fails:

```text
3 passed in 0.02s
```

## What makes a good test

- Use inputs where you know the correct answer by hand.
- Include edge cases: empty, zero, one, and unusual values.
- Test one idea per test, and name it so that a failure explains itself.
- Do not copy the code's logic into the test. That only proves the code agrees with itself.

## Hands-on

### Your turn

Write down, in words, one more test for `total_amount`. Think of an input and the exact
answer.

<Checkpoint question="Show some good answers">
	For example: one amount `["1500.50"]` gives `1500.50`; two amounts `["0.01",
	"0.01"]` give `0.02`; and an amount with zero cents `["10"]` gives `10`.
</Checkpoint>

## Common mistakes

- **Writing tests that repeat the code.** Work out the answer by hand instead.
- **Testing only the easy case.** Add empty and odd inputs.
- **Ignoring a failing test.** A failure is information. Read it.
- **Trusting AI-written tests blindly.** The expected values may be wrong. Check them.
- **Never running tests.** Run them before each commit.

## Ask your AI assistant

<PromptExample>
	<Fragment slot="lousy">Write tests.</Fragment>
	<Fragment slot="whatGoesWrong">
		The assistant writes tests that re-implement the function or only check that
		it runs, and they pass even if the code is wrong.
	</Fragment>
	<Fragment slot="good">
		Here is a Python function total_amount(amounts) that adds amounts written as
		text, using Decimal. Write three pytest tests: a normal case, an empty list,
		and a case with cents such as 0.10 and 0.20. Work out each expected value by
		hand and show the arithmetic in a comment. Do not call the function to
		compute the expected value.
	</Fragment>
	<Fragment slot="whyItWorks">
		It provides the **input** (the function) and the **task**, and the
		**constraint** forbids circular tests. Comments with the arithmetic are
		built-in **verification**.
	</Fragment>
	<Fragment slot="check">
		Redo the arithmetic yourself. Then temporarily break the function on purpose
		and confirm that at least one test fails.
	</Fragment>
</PromptExample>
