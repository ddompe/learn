## Why this matters

You know this folder:

```text
monthly_report.xlsx
monthly_report_v2.xlsx
monthly_report_v2_final.xlsx
monthly_report_v2_final_REAL.xlsx
monthly_report_v2_final_REAL_Daniela_fixed.xlsx
```

Which one is current? What changed between them? Who changed it, and why? Nobody
knows, and you cannot go back to the good version from Tuesday without guessing.
**Version control** is a system built to answer those questions.

When an AI assistant edits your files, this matters even more. You want an easy way to
see exactly what changed, and to undo it.

<CaseStudy>
	Daniela keeps a copy of the monthly script for every change. Last month she
	fixed a bug and broke the totals. She cannot tell which of her six copies had
	the working version.
</CaseStudy>

## Snapshots and history

Version control keeps a series of **snapshots** of your project. Each snapshot records
the state of all your files at one moment, with a short message that says what you
changed and why. The list of snapshots is the **history**.

<Mermaid
	diagram={`flowchart LR
  A["Snapshot 1: first version"] --> B["Snapshot 2: fix dates"]
  B --> C["Snapshot 3: remove duplicates"]
  C --> D["Snapshot 4: add chart"]`}
/>

With a history you can:

- See what changed between any two snapshots.
- Go back to an earlier snapshot.
- Read why each change was made.
- Try something risky, knowing you can undo it.
- Work with other people without overwriting each other (lesson 3.6 and beyond).

There is one working folder with the current files. The history lives beside it, so you
do not multiply the files.

## Git

**Git** is the most widely used version control system. It is free and works on your
own computer, without internet. Nearly all software teams use it. You will use it through
VS Code and, a little, through the terminal.

A project tracked by Git is a **repository**, or repo.

Git is built for text files, like code and CSV. It can store Excel files, but it cannot
show what changed inside them. That is one reason why this course keeps its work in text.

## Version control is not a backup

A repository on your computer does not protect you from losing the computer. Sync
services (lesson 1.6) copy files but keep no meaningful history. For both, you push the
repository to a remote copy (lesson 3.6).

## Hands-on

### Your turn

Look at your own documents folder. Find one file that exists in several versions.

1. How do you know which is the latest?
2. Could you say what changed between the last two?
3. Could you return to the version from a month ago?

<Checkpoint question="What does this show?">
	Most people answer "not reliably" to at least two of the three. Version
	control makes each answer reliable.
</Checkpoint>

## Common mistakes

- **Thinking Git is only for programmers.** Anyone with files that change over time can use it.
- **Treating Git as a backup.** Without a remote copy, a lost computer means lost history.
- **Believing a repository is a special folder you cannot open.** It is a normal folder
  with a hidden `.git` folder inside.
- **Expecting to compare Excel files line by line.** Git sees them as binary files.
- **Waiting until the project is big.** Start on day one.

## Check yourself

<Checkpoint question="What is a snapshot?">
	A record of the state of all your files at one moment, with a message
	describing the change.
</Checkpoint>

<Checkpoint question="Is Git a backup?">
	No. A repository only on your computer is lost with the computer. A remote
	copy provides the backup.
</Checkpoint>

<Checkpoint question="Why does Git work best with text files?">
	It can show line-by-line changes in text. It cannot see inside binary files
	such as Excel.
</Checkpoint>
