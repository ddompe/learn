- Explain why a secret committed to Git stays in the history.

## Why this matters

In lesson 1.12 you learned that an API key must stay secret. Git makes leaking one very
easy: you commit a file, push it, and the key is now in the history, on GitHub, and
possibly copied by others. Deleting the file in a later commit does not help, because the
old snapshot still has it. Automated scanners look for exposed keys within minutes of a
push to a public repository.

<CaseStudy>
	Café Central uses a service that needs a key. Daniela must write a program
	that uses the key without ever putting the key in the repository.
</CaseStudy>

## The plan

1. Put the secret in a file named `.env`, which is not tracked by Git.
2. Tell Git to ignore that file, using `.gitignore`.
3. Make the program read the secret from the environment.
4. Share only an example file with a fake value, so others know what to fill in.

## The .gitignore file

A file named `.gitignore` lists names and patterns that Git must not track. One entry per
line. Lines that start with `#` are comments.

<Example file="part03/07_gitignore.txt" />

Create `.gitignore` **before** the first commit that could contain the secret. Git ignores
only files that it is not yet tracking. If you already committed the secret, ignoring it
does not remove it.

## The .env file

The `.env` file holds `NAME=value` lines. The real file stays private. A copy with a fake
value, named for example `.env.example`, is safe to commit.

<Example file="part03/07_env_example.txt" />

Many tools load `.env` automatically. Your program then reads the value from the
environment, which you met in lesson 1.10.

<Example file="part03/07_env.py" />

Without the variable set, the program explains what to do. With it set, the program
confirms that it found the key, but prints only its length, never the key itself.

## If a secret was committed

1. **Revoke the key** on the service's website straight away, and create a new one. This
   is the step that matters. Assume anyone could have copied it.
2. Remove it from your files and keep it in `.env`.
3. Rewriting history is a delicate procedure. Ask for help before trying it. Revoking
   the key is what protects you.

## Hands-on

### Worked example

1. Create `.gitignore` in your project with the lines from the example.
2. Create `.env` with a **fake** value such as `CAFE_API_KEY=not-a-real-key`.
3. Run `git status`. The file `.gitignore` appears as new, but `.env` does not.
4. Commit `.gitignore` with a clear message.

### Your turn

Why would adding `.env` to `.gitignore` after committing it not solve the problem?

<Checkpoint question="Show the answer">
	Git already stores the file in earlier snapshots, and `.gitignore` only
	affects files that are not yet tracked. The key stays in the history, so it
	must be revoked.
</Checkpoint>

## Common mistakes

- **Adding `.gitignore` too late.** Create it at the start.
- **Committing `.env.example` with a real key.** The example must hold a placeholder.
- **Thinking a private repository is safe for secrets.** People are added, repositories
  become public, and laptops get lost. Keep secrets out anyway.
- **Hard-coding the key in the program "just for now".** It tends to stay.
- **Skipping the revoke.** Deleting is not enough.
