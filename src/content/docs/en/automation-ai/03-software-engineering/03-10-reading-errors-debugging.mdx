## Why this matters

Programs fail. It is normal, and it is not a sign that you did something wrong. What
matters is whether you can read the message. An error message is the computer telling
you what it could not do, and where. Most beginners panic and look at none of it. This
lesson teaches you to read it.

## Anatomy of a traceback

When a Python program fails, it prints a **traceback**: the list of steps that led to the
failure. Here is the shape, from a program that tries to read a missing file.

<Example file="part03/10_traceback.py" />

The output shows the error type, then the call chain. The program started at the bottom
of the file, called `main`, which called `read_sales`, which tried to read the file.

A real traceback has these parts:

| Part                     | What it tells you                           |
| ------------------------ | ------------------------------------------- |
| The last line            | The error type and message: what went wrong |
| The file and line number | Where in your code it happened              |
| The lines above          | The path of calls that led there            |

**Read from the bottom.** The last line says what went wrong. Then find the lines that
name your own files.

Common error types:

- `FileNotFoundError`: the path is wrong (lesson 1.4).
- `UnicodeDecodeError`: wrong encoding (lesson 1.7).
- `KeyError`: you asked for a column or name that is not there.
- `ModuleNotFoundError`: a package is not installed (lesson 3.8).
- `SyntaxError`: the program is not written correctly.

## The debugger

A **debugger** runs your program one step at a time so that you can look inside. In VS
Code, you click in the margin next to a line number to set a **breakpoint**, a red dot
where the program will stop. When it stops, you can see the values of variables, and
step to the next line. It answers "what is the value here?", without guessing.

You will use the debugger properly in Part 4, once you run Python yourself. For now, know
that it exists, and what a breakpoint is.

## Asking an assistant about an error

Give it what it needs:

1. The **whole** error message, not just the last line.
2. The **code** around the line that failed.
3. What you were **trying to do** and what you expected.
4. What **changed** since it last worked.
5. Your **system** if it might matter.

Do not include secrets. Remove keys, passwords, and personal data from the message.

## Common mistakes

- **Reading only the first line.** The useful part is the last line, and the line
  naming your file.
- **Pasting only "it doesn't work".** An assistant cannot help without the message.
- **Changing several things at once.** Change one thing, run, and observe.
- **Panicking.** An error is information.
- **Trusting a fix you do not understand.** Ask why it works.
