## Why this matters

A computer stores only numbers. For text, it needs a rule that says which number stands
for which letter. That rule is an **encoding**. If the program that writes a file and
the program that reads it use different rules, letters become nonsense. For anyone
working with Spanish names and accents, this is a daily problem.

	names are not wrong in the file. The program is reading them with the wrong

</CaseStudy>

## From letters to bytes

An encoding is a table that maps characters to numbers, and numbers to bytes.

<Mermaid
	diagram={`flowchart LR
  A["Text: Categoría"] -->|"encode with a rule"| B["Bytes"]
  B -->|"decode with a rule"| C["Text again"]`}
/>

Three names matter:

- **ASCII** is the oldest rule. It covers 128 characters: English letters, digits, and
  punctuation. It has no accented letters.
- **Unicode** is a huge catalogue that gives a number to nearly every character in every
  language, plus emoji. It is the list, not the byte format.
- **UTF-8** is the most common way to write Unicode as bytes. English letters take one
  byte. Accented letters like `í` take two. Other symbols take up to four.

Older systems used other rules. **Latin-1** (and its Windows cousin, cp1252) uses one
byte per character and covers Western European accents. When a file written in UTF-8 is
read as Latin-1, each two-byte letter becomes two wrong characters. This garbling is
called **mojibake**, a Japanese word for "character change".

The classic sign: `ñ` becomes `Ã±` and `í` becomes `Ã` followed by an invisible
character.

## Hands-on

### Worked example

<Example file="part01/07_encodings.py" />

The word `Categoría` encodes to bytes in which the letter `í` is the two bytes `\xc3\xad`.
When those bytes are decoded using Latin-1, each byte becomes its own character, which
gives `CategorÃ­a`. The second character after `Ã` is invisible, which is why it looks
like a soft hyphen or nothing. Encoding back with Latin-1 and decoding with UTF-8
repairs the text, because the original bytes were never lost.

The key idea: **the bytes were fine. Only the reading rule was wrong.**

## Common mistakes

- **Saving after the damage.** If you open a UTF-8 file with the wrong encoding and save
  it, the mangled text is written into the file. Always keep the original.
- **Fixing characters one by one.** The pattern is systematic. Change the encoding
  instead.
- **Assuming UTF-8 everywhere.** Files from older systems or some Excel exports use
  other encodings.
- **Confusing the font with the encoding.** A missing-glyph square is a font problem.
  Strange extra letters are an encoding problem.
- **Ignoring the BOM.** Some tools add a hidden mark at the start of a UTF-8 file. If the
  first column header looks odd, this may be why. Part 5 returns to it.

## Check yourself

<Checkpoint question="What is an encoding?">
	A rule that maps characters to numbers and bytes, and back.
</Checkpoint>

<Checkpoint question="Why does `í` turn into `Ã` plus another character?">
	The file is UTF-8 and stores `í` as two bytes. A program reading it as Latin-1
	turns each byte into its own character.
</Checkpoint>

<Checkpoint question="What is the difference between Unicode and UTF-8?">
	Unicode is the catalogue of characters and their numbers. UTF-8 is one way to
	store those numbers as bytes.
</Checkpoint>
