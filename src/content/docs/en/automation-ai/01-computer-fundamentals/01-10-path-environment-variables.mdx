## Why this matters

You type a command, and the computer answers "command not found". The program is
installed, so why can't the shell see it? The answer is almost always PATH. This is the
most common beginner error when installing developer tools, and you will meet it again
in Parts 3 and 4.

<CaseStudy>
	Lucía installs a tool for the Café Central project. In a new terminal, she
	types its name and gets "not found". The tool is on her disk. The shell just
	doesn't know where to look.
</CaseStudy>

## How the shell finds programs

When you type a command such as `git`, the shell does not search the whole disk. That
would be slow. Instead it checks a short list of folders, in order, and runs the first
match. That list is called **PATH**.

<Mermaid
	diagram={`flowchart TD
  A["You type: git"] --> B["Shell reads PATH, a list of folders"]
  B --> C{"Is git in the first folder?"}
  C -- Yes --> D["Run it"]
  C -- No --> E{"Next folder?"}
  E -- Yes --> C
  E -- "List ended" --> F["Error: command not found"]`}
/>

So "command not found" means "not in any folder on PATH". The fix is either to add the
program's folder to PATH, or to use the installer's option that does it for you.

## Environment variables

PATH is one example of an **environment variable**: a named piece of text that the
system keeps for programs to read. Others hold your user name, your home folder, or
settings for a tool. Programs read them when they start.

Environment variables are also a common place to keep secrets, such as API keys,
outside of your files. Lesson 1.12 and Part 3 return to that.

## Hands-on

### Worked example: read a variable

<OsTabs>
  <Fragment slot="windows">
```text
PS> $env:USERNAME
PS> $env:PATH -split ';'
```
  </Fragment>
  <Fragment slot="macos">
```text
$ echo $USER
$ echo $PATH | tr ':' '\n'
```
  </Fragment>
</OsTabs>

The first command prints your user name. The second prints the PATH, split into one
folder per line. The order matters: the shell uses the first match.

### Set a variable for this session

<OsTabs>
  <Fragment slot="windows">
```text
PS> $env:CAFE_REPORT_NAME = "2024-01"
PS> $env:CAFE_REPORT_NAME
```
  </Fragment>
  <Fragment slot="macos">
```text
$ export CAFE_REPORT_NAME=2024-01
$ echo $CAFE_REPORT_NAME
```
  </Fragment>
</OsTabs>

This variable lives only in the current terminal window. Close the window, and it is
gone. That is a safe way to experiment. Making a variable permanent depends on the
system, so we leave it for when you need it.

## Common mistakes

- **Installing a tool and using the old terminal.** PATH is read when the terminal
  starts. Open a new window after installing.
- **Editing PATH without understanding it.** A wrong edit can hide other programs.
  Prefer installers that offer to do it.
- **Having two versions of a program.** The one earlier in PATH wins, which can confuse.
- **Typing `$` or `$env:` in the wrong shell.** The syntax differs between systems.
- **Putting secrets in files you share.** Keep them in environment variables or ignored
  files. See Part 3.
