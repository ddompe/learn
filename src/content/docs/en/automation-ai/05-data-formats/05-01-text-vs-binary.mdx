## Why this matters

Data arrives in many formats, and each one asks something different of you. Before you
open a file, you should know what kind it is: can you read it with your eyes, compare two
versions, give it to an AI assistant, or put it under Git? The answer depends on one
split: text or binary.

<CaseStudy>
	Daniela receives Café Central's sales as a CSV, the customer list as JSON, a
	monthly summary as an Excel workbook, and a supplier invoice as a PDF. Four
	files, and four very different ways of working with them.
</CaseStudy>

## Text and binary

Lesson 1.5 introduced the idea. A **text format** stores characters, so a text editor can
show it. CSV, JSON, YAML, TOML, and Markdown are text formats. A **binary format**
stores bytes that only the right program can interpret. Excel `.xlsx`, Word `.docx`, PDF,
and Parquet are binary.

## What text gives you

1. **You can read it.** Open it in any editor and see what is there.
2. **You can compare versions.** A change shows as the exact lines that changed.
3. **Git works well.** History and review are meaningful (lesson 3.4).
4. **Almost any tool reads it.** Python, Excel, databases, and AI assistants.
5. **It is robust.** If part of a text file is damaged, the rest is usually readable.

The first part shows the benefit. Changing one amount changes exactly one line, and the

## What binary gives you

Binary formats are not bad. They can be **smaller**, **faster**, and carry **richer
content**: formatting, charts, and types. Excel keeps formulas and colours. Parquet
(lesson 5.9) stores large tables compactly. The trade-off is that you need a program,
or a library, to open them.

## Choosing a format

Ask what the file is for.

| If the file is...                     | Prefer       |
| ------------------------------------- | ------------ |
| A table to exchange between tools     | CSV          |
| Nested records, or data for a program | JSON         |
| Settings a person edits               | YAML or TOML |
| Text for people and AI to read        | Markdown     |
| A report for people to read and print | PDF or Word  |
| A very large table for analysis       | Parquet      |

## Hands-on

### Your turn

Café Central keeps its price list in an Excel file. The team edits it each month and wants
to see who changed what. What would you suggest?

<Checkpoint question="Show a sample answer">
	Keep the price list as a CSV, which is text, and store it in Git. Each change
	then shows as a line, with an author and a message. Excel can still open and
	edit the CSV (carefully, see lesson 5.2).
</Checkpoint>

## Common mistakes

- **Storing data in a "pretty" binary format by default.** Ask who will use it and how.
- **Assuming text means simple.** Text formats have rules and traps too.
- **Putting large binary files in Git.** History grows, and changes are opaque.
- **Opening a binary file in a text editor and saving.** It destroys the file.
- **Choosing a format because it is familiar.** Choose it because it fits the use.
