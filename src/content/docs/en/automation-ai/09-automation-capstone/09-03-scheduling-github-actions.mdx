## Why this matters

Your computer must be on for a local schedule to work. **GitHub Actions** runs jobs on
GitHub's computers, which are always available, whenever a trigger fires. This site itself
is built and published that way. For a project already on GitHub (lesson 3.6), a monthly
job needs one file.

The details of GitHub Actions, such as the free allowance and the versions of the
actions, change. The structure below is stable. Check the details in the official
documentation. Last verified on 2026-10-03.

## A workflow

A **workflow** is a YAML file (lesson 5.4) in the folder `.github/workflows/` of the
repository. It says **when** to run, and which **steps** to take.

<Example file="part09/monthly_report.yml" />

Read it from the top:

- `on` lists the triggers. `schedule` uses the same cron syntax as lesson 9.2. GitHub reads the time as **UTC**: 13:00 UTC is 07:00 in Costa Rica. `workflow_dispatch` adds a button to run it by hand.
- A `job` runs on a fresh virtual machine, `ubuntu-latest`.
- The `steps` check out your code, set up uv, run the tests, run the pipeline, and upload
  the `output/` folder as an **artifact**: a downloadable result attached to the run.
- If a step fails, the job stops, and GitHub marks the run as failed. That is why the exit
  codes of lesson 9.1 matter.

Notice that the tests run **before** the pipeline. A report is not produced from code that
fails its own tests.

<Mermaid

To use it, copy the file into `.github/workflows/` in your repository, and commit and push it.
Then open the **Actions** tab on GitHub to see the runs and download the artifact. Use the
**Run workflow** button to try it right away instead of waiting for the date.

## Limits and cautions

1. **Where does the data come from?** The job runs in the cloud, so it cannot read files on your computer.
   The input must be in the repository, or fetched from somewhere the job can reach.
2. **Privacy.** Do not put customer data into a **public** repository, and think twice about using
   private data in the cloud at all (lesson 2.8). The practice data of this course is
   fictional, so it is safe.
3. **Secrets** such as API keys go in the repository settings under secrets, and are used in the
   workflow as variables. Never write them in the file (lesson 3.7).
4. **Timing.** Scheduled runs can start late when GitHub is busy. For a monthly report, that does not matter.
5. **Inactivity.** GitHub may disable scheduled workflows in repositories without recent activity.
   Check the current rule in the documentation.
6. **Cost.** There are free allowances, and they differ for public and private repositories.

## Common mistakes

- **Reading the schedule in local time.** It is UTC.
- **Expecting local files to be there.**
- **Putting private data in a public repository.**
- **Keys in the workflow file.**
- **A workflow with no tests.** A broken change then goes straight into a monthly report.
- **Not using the manual trigger to test.**
