## Why this matters

A script that you run by hand, watching the screen, can be sloppy. A script that runs by
itself at 7 am on the first of the month cannot. Nobody is watching. It must find its
settings, record what it did, and, above all, tell someone when it fails. The worst
automation is the one that fails quietly and leaves an old report in place.

## A config file

Settings that change, such as the file locations, the month, and limits, live in a file.
The pipeline uses TOML (lesson 5.5):

<Example file="part09/pipeline_config.toml" />

Paths are relative to the config file, so the project works wherever it is copied. A
change of month needs an edit of one line, not the code.

## Command-line options

The `argparse` module from the standard library reads options such as `--month 2024-01`,
`--output-dir`, and `--verbose`. It also writes the `--help` text for you. Options **override** the
config for a single run, so you can try another month without editing anything.

Run `uv run python pipeline.py --help` to see them.

## Logging

Instead of `print`, the script uses the `logging` module. It gives each message a **level**:

| Level   | Use                                               |
| ------- | ------------------------------------------------- |
| DEBUG   | Detail for finding problems (each cleaning step)  |
| INFO    | Normal progress (rows read, total, files written) |
| WARNING | Something odd, but the run continues              |
| ERROR   | The run cannot continue                           |

The log goes to two places: the screen (INFO and above, or everything with `--verbose`) and
a file `pipeline.log` with timestamps. When a scheduled run fails at night, the file is
how you find out why.

## Fail loudly, fail early

- **Validate the input first.** The pipeline checks that the file exists, and that the month has
  at least `min_rows` rows. A file for the wrong month fails with "Only 0 rows for 2023-12;
  expected at least 100. Is this the right file?" rather than producing an empty report.
- **Two kinds of failure,** two exit codes. A problem with the input, which a person can fix,
  returns **2** with a plain message. Anything unexpected returns **1** and logs the full
  traceback (lesson 3.10).
- **Success returns 0.** Schedulers and workflows use the exit code to decide whether a job
  failed (lessons 9.2 and 9.3).
- **Never overwrite the input,** and write the results to a separate output folder.
- **Make it safe to rerun.** Running twice for the same month gives the same files.

## Tests

The tests for this script run the whole pipeline into a temporary folder, check the CSV that
it writes, and trigger each failure: a missing file, a wrong month, and an unexpected
error. They check the exit codes and the messages. Failure paths are the ones that nobody
tests by hand, so they are the ones that most need a test.

## Common mistakes

- **Hard-coded paths.** Put them in the config, relative to it.
- **`print` instead of logging.** There is no level and no file.
- **Catching every error and carrying on.** That produces wrong reports silently.
- **Log messages with secrets or personal data.**
- **No exit code.** The scheduler thinks that a failure was a success.
- **Testing only the happy path.**

## Check yourself

<Checkpoint question="Why log to a file as well as the screen?">
	When the script runs unattended, the file is the only record of what happened.
</Checkpoint>

<Checkpoint question="What do exit codes tell a scheduler?">
	Zero means success, anything else means failure.
</Checkpoint>

<Checkpoint question="Why validate the input before processing?">
	A wrong file should stop the run with a clear message, instead of producing a
	wrong or empty report.
</Checkpoint>
