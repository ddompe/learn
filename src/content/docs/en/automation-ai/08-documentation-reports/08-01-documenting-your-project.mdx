## Why this matters

Six months from now, you will open your own project and not remember how to run it. A
colleague who takes it over will be even more lost. Documentation is not a
formality. It is what turns a script that only you can run into a tool that a team can use.
It is also the first thing an AI assistant reads to understand your project.

<CaseStudy>
	Daniela goes on holiday, and Mateo must produce the February report. All he
	has is the project folder. A good README means he can do it without calling
	her.
</CaseStudy>

## The README

A **README** is a Markdown file (lesson 5.6) at the top of the project, named `README.md`.
Git hosting sites like GitHub show it on the project's front page. It answers the
questions a newcomer asks, in order:

1. **What is this?** One or two sentences.
2. **What does it do?** The main steps.
3. **What do I need?** Tools and versions.
4. **How do I run it?** The exact commands.
5. **What goes in and what comes out?** Input files and results.
6. **What should I know?** Decisions and traps.
7. **How do I check it works?** The tests.
8. **Who do I ask?** A contact.

Notice what this README does well:

- The commands can be copied and run.
- It states the decisions that are easy to forget: slash dates are read day first, amounts

- It is short. A README that nobody finishes reading is not documentation.

## Project notes and decisions

Not everything fits in the README. Keep a short `notes.md` or a `docs/` folder for:

- **Decisions:** what you chose, what you rejected, and why. A short entry with a date is enough.
- **Known problems:** things you know are wrong and have not fixed.
- **Data notes:** where the data comes from and what its quirks are.

Write these while you remember. They cost minutes now and save hours later. Commit them
with the code (Part 3), so the history shows when each was written.

## Comments and docstrings

In the code itself, write a **docstring** at the top of each function (lesson 4.12) saying what it does,
and a short comment only where the reason is not obvious. Comments that repeat the code
("add one to count") only add noise.

## Hands-on

### Worked example

1. Create `README.md` in your project, with the headings from the example.
2. Fill in each one for your own project. Be specific about commands.
3. Ask a colleague, or an AI assistant, to follow it step by step. Where do they get stuck?

## Common mistakes

- **No instructions.** The README says what the project is but not how to run it.
- **Commands that don't work.** Test them on a clean copy.
- **Out of date.** Update the README in the same commit as the change.
- **Writing for yourself.** Write for someone who has never seen the project.
- **Too long.** Link to longer notes instead.
- **Letting an AI invent features.** Check every claim.

## Check yourself

<Checkpoint question="What questions should a README answer?">
	What the project is and does, what is needed, how to run it, what goes in and
	out, what to know, how to test it, and whom to ask.
</Checkpoint>

<Checkpoint question="Why record decisions?">
	So that others, and you later, understand why choices were made and do not
	undo them by accident.
</Checkpoint>

<Checkpoint question="How can you test a README?">
	Ask someone to follow it on a clean copy and see where they get stuck.
</Checkpoint>
