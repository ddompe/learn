## Why this matters

Real files are missing, amounts contain `N/A`, and networks fail. A program that crashes
with an unreadable message is hard to use. A program that ignores errors silently is
worse, because it gives wrong results without warning. Good error handling sits in the middle: handle
what you expect, and explain what you cannot fix.

	program to say exactly which file or value is wrong, not to print a wall of
	red text or quietly skip rows.
</CaseStudy>

## Exceptions

When something goes wrong, Python **raises an exception**, such as `FileNotFoundError` or
`ValueError`. If nothing handles it, the program stops and prints a traceback
(lesson 3.10).

You handle one with `try` and `except`:

```text
try:
    risky_step()
except FileNotFoundError:
    explain_the_problem()
```

The code in `try` runs. If that exact kind of error happens, the `except` block runs
instead. Other errors still stop the program, which is what you want.

## Rules of thumb

1. **Catch only what you expect,** and name the type.
2. **Never write a bare `except:` or `except Exception: pass`.** It hides bugs.
3. **Write messages for a human:** what failed, with which value, and what to check.
4. **Decide what to do with bad rows:** stop, skip and report, or fix. Do not skip in silence.

## Common mistakes

- **Bare `except:`.** It catches everything, including your own typos.
- **`except ...: pass`.** The error disappears and so does the evidence.
- **Messages like "Error".** Say what and where.
- **Catching too early.** Let errors travel up to the code that can decide what to do.
- **Using errors for normal control flow.** Check simple conditions with `if`.
