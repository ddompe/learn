## Why this matters

A Python **project** is a folder with your code plus a description of what it needs. This
lets the project run the same on your laptop, a colleague's, and a server. Without
projects, packages pile up in one shared place, and different tasks need different,
conflicting versions.

<CaseStudy>
	Daniela creates a project called `cafe-report`. It lists pandas as a
	dependency. When she shares the project, a colleague runs one command and gets
	the same setup.
</CaseStudy>

## Create a project

In a terminal, move to the folder where your projects live, and run:

```text
uv init cafe-report
cd cafe-report
```

uv creates a folder with a few files:

| File              | What it is                                                           |
| ----------------- | -------------------------------------------------------------------- |
| `pyproject.toml`  | The project description: name, version, Python version, dependencies |
| `main.py`         | A starter program                                                    |
| `.python-version` | The Python version this project uses                                 |
| `README.md`       | A place to describe the project                                      |

It also prepares the folder for Git. If your folder is already a repository, that is fine.

## Reading pyproject.toml

**TOML** is a text format for settings. It has `[sections]` and `name = value` lines.
You saw a sample in lesson 3.8.

<Example file="part03/08_pyproject_example.toml" />

You will edit it rarely by hand. Commands like `uv add` change it for you.

## Add a package

```text
uv add pandas
```

This does three things:

1. It adds `pandas` to the `dependencies` in `pyproject.toml`.
2. It creates a **virtual environment**, in a hidden folder called `.venv`, and installs
   the package there.
3. It writes `uv.lock`, a record of the exact versions (lesson 3.8).

A **virtual environment** is a private folder of packages for one project. Two projects
can use different versions without clashing. You never edit `.venv` by hand, and you do
not commit it to Git.

## Share a project

Commit `pyproject.toml`, `uv.lock`, `.python-version`, and your code. Do not commit `.venv`.
Add it to `.gitignore` (lesson 3.7). A colleague then clones the repository and runs:

```text
uv sync
```

which recreates the environment from the lock file.

## Hands-on

### Worked example

1. Create the project with `uv init cafe-report` and open the folder in VS Code.
2. Open `pyproject.toml`. Find the name, the Python version, and the dependencies list.
3. Run `uv add pandas`. Look at `pyproject.toml` again, then find `uv.lock` and `.venv`.
4. Add `.venv/` to `.gitignore` and make a commit.

## Common mistakes

- **Working outside the project folder.** Run uv commands inside the project.
- **Committing `.venv`.** It is large and machine-specific.
- **Editing the lock file by hand.** Let uv write it.
- **Mixing in pip.** Use `uv add`. Mixed tools lead to confusion.
- **Copying the `.venv` folder to another computer.** Use `uv sync` instead.
