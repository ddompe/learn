## Por qué importa

Este es el proyecto para el que se ha preparado todo el curso. Vas a juntar las piezas:
los fundamentos de computación, un prompt claro, Git, Python, la limpieza de datos, los
gráficos, un informe y un horario. El resultado es una herramienta que hace lo que a
Daniela le tomaba un día, y que ella puede entregar a otra persona.

Usarás un asistente de IA para casi todo el tecleo. Tu trabajo es lo que el asistente no
puede hacer por ti: decidir qué es correcto, comprobar y mantener cada paso pequeño.

<CaseStudy>
	Café Central necesita que el informe mensual se construya solo. El encargo de
	Daniela: poner el archivo de ventas en una carpeta, ejecutar un comando y
	obtener los totales limpios, el gráfico y el informe en Word, PDF y HTML. Si
	algo está mal con el archivo, que me lo diga con claridad.
</CaseStudy>

## Los requisitos

Tu pipeline está terminado cuando cumple cada elemento. Están escritos para que puedas
comprobar cada uno.

### Datos

1. Lee el CSV de ventas, separado por punto y coma y en UTF-8, de la carpeta `data`.
2. Interpreta los tres formatos de fecha (las fechas con barras van con el día primero) y
   los tres formatos de monto.
3. Elimina las filas duplicadas exactas, unifica las variantes de escritura de las
   categorías y conserva, marcadas, las filas sin cliente.
4. Los montos son decimales exactos. Los datos limpios de enero tienen 240 filas y un
   total general de 474,061.00 colones.

### Comportamiento

1. Los ajustes vienen de un archivo de configuración; el mes y la carpeta de salida se pueden anular en la línea de comandos.
2. Escribe un archivo de registro e imprime el progreso. Un archivo equivocado o ausente detiene la ejecución con un mensaje claro y el código de salida 2.
3. Escribe los totales por categoría como CSV y como un archivo de Excel con formato.
4. Produce el informe, con un gráfico semanal con título que empieza en cero, una tabla por categoría y cifras en el texto que provienen de los datos, en HTML, Word y PDF.
5. El informe se puede generar para una sola categoría con un parámetro.

### Calidad

1. Las pruebas cubren los intérpretes de formatos, la limpieza (incluido el resultado de 240 filas) y cada fallo.
2. Un README dice qué hace, cómo ejecutarlo y qué decisiones se tomaron.
3. El proyecto está en Git con commits claros, en un repositorio privado, sin secretos ni datos privados.
4. Se ejecuta de forma programada, en tu computadora o en GitHub Actions, y lo has visto ejecutarse al menos una vez desde el horario.

## Cómo construirlo con un asistente

El método que funciona es el mismo en cada paso: **paso pequeño, prompt claro, ejecutar,
comprobar, hacer commit.**

| Paso | Construye                                                | Comprueba antes de hacer commit                                 |
| ---- | -------------------------------------------------------- | --------------------------------------------------------------- |
| 1    | Proyecto con uv; esqueleto del README; `.gitignore`      | `uv run python --version`; primer commit                        |
| 2    | Intérpretes: `parse_amount`, `parse_date`, `simplify`    | Pasan las pruebas con valores calculados a mano                 |
| 3    | `clean_sales` con registro                               | 246 filas de entrada, 240 de salida; los conteos coinciden      |
| 4    | Totales; comprobación del total general                  | 474,061.00; un total manual de una categoría                    |
| 5    | Configuración, opciones CLI, registro, códigos de salida | Provoca los fallos de archivo ausente y mes equivocado          |
| 6    | Salidas en CSV y Excel                                   | Abre el archivo de Excel; acentos y formato numérico bien       |
| 7    | El informe de Quarto; parámetro; tres formatos           | Los totales del texto igualan la tabla; el eje empieza en cero  |
| 8    | Pruebas del pipeline, README terminado                   | `uv run pytest` en verde; un desconocido puede seguir el README |
| 9    | Push a un repositorio privado                            | Sin secretos; `.env` ignorado                                   |
| 10   | Prográmalo                                               | Ejecútalo dentro de dos minutos y luego a la hora real          |

Ya escribiste la mayor parte del código de los pasos 2 a 7 antes en el curso. Puedes
reutilizarlo, adaptarlo o reconstruirlo con el asistente. Si lo reconstruyes, compara lo
que obtienes con tu versión anterior: es una buena manera de encontrar el error de un
asistente.

### Reglas de trabajo

1. **Un paso por prompt.** Nunca pidas todo el pipeline de una vez.
2. **Dale los hechos al asistente:** la estructura del archivo, los formatos y las reglas
   exactas.
3. **Escribe o revisa primero la prueba** cuando puedas: calcula a mano la respuesta
   esperada.
4. **Lee cada línea** antes de aceptarla (lección 3.3).
5. **Haz commit después de cada paso** que funcione, con un mensaje claro (lección 3.5).
6. **Cuando algo se rompa,** dale al asistente el traceback completo y el código
   (lección 3.10).
7. **Sin datos privados en los prompts** (lección 2.8). Los datos del curso son
   ficticios.

## Manos a la obra

### El proyecto final

Trabaja la tabla de arriba. Lleva un registro breve de los problemas que encuentres y de
cómo los resolviste. Es la mejor documentación que puedes dejar para la siguiente persona,
y para ti mismo.

### Ahora tú

Elige tu propia extensión, lo bastante pequeña para terminarla en una hora:

1. Añade una opción `--category` al pipeline que restrinja los totales.
2. Añade una comprobación que avise si algún día no tiene ventas.
3. Añade el archivo de clientes e informa de las ventas por ciudad (lección 6.6).
4. Envíate el informe: escribe la ruta de salida en el registro de una forma en la que
   puedas hacer clic.

<Checkpoint question="¿Cómo sabes que una extensión está terminada?">
	Tiene una prueba que falla sin el cambio y pasa con él, el README la menciona
	y está registrada con un commit de mensaje claro.
</Checkpoint>

## Errores comunes

- **Pedirlo todo de una vez.** Produce un resultado grande, sin pruebas e incorrecto.
- **Saltarte las comprobaciones** porque el asistente sonaba seguro (lección 2.6).
- **Hacer commit de datos o claves.**
- **Programar antes de que funcione a mano.**
- **Cambiar los datos para que la prueba pase.**
- **Sin README.** En seis meses el proyecto es un misterio.
- **No observar nunca la primera ejecución programada.**
