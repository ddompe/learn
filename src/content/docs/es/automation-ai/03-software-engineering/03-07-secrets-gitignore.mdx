<LessonGoals>

- Explicar por qué un secreto del que se hizo commit en Git permanece en el historial.
- Usar un archivo `.gitignore` para mantener archivos fuera de Git.
- Guardar una clave en un archivo `.env` y leerla desde un programa.

</LessonGoals>

## Por qué importa

En la lección 1.12 aprendiste que una clave de API debe mantenerse en secreto. Git hace
muy fácil filtrar una: haces commit de un archivo, lo envías (push) y la clave queda en
el historial, en GitHub y posiblemente copiada por otras personas. Borrar el archivo en
un commit posterior no sirve, porque la instantánea anterior todavía lo contiene. Hay
escáneres automáticos que buscan claves expuestas pocos minutos después de un push a un
repositorio público.

<CaseStudy>
	Café Central usa un servicio que necesita una clave. Daniela debe escribir un
	programa que use la clave sin poner nunca la clave en el repositorio.
</CaseStudy>

## El plan

1. Pon el secreto en un archivo llamado `.env`, que Git no controla.
2. Dile a Git que ignore ese archivo, usando `.gitignore`.
3. Haz que el programa lea el secreto desde el entorno.
4. Comparte solo un archivo de ejemplo con un valor falso, para que otros sepan qué
   deben completar.

## El archivo .gitignore

Un archivo llamado `.gitignore` lista los nombres y patrones que Git no debe controlar.
Una entrada por línea. Las líneas que empiezan con `#` son comentarios.

<Example file="part03/07_gitignore.txt" />

Crea `.gitignore` **antes** del primer commit que pueda contener el secreto. Git ignora
solo los archivos que todavía no controla. Si ya hiciste commit del secreto, ignorarlo
no lo elimina.

## El archivo .env

El archivo `.env` contiene líneas con el formato `NOMBRE=valor`. El archivo real se
mantiene privado. Una copia con un valor falso, llamada por ejemplo `.env.example`, es
segura para hacer commit.

<Example file="part03/07_env_example.txt" />

Muchas herramientas cargan `.env` automáticamente. Entonces tu programa lee el valor
desde el entorno, que conociste en la lección 1.10.

<Example file="part03/07_env.py" />

Si la variable no está definida, el programa explica qué hacer. Si está definida, el
programa confirma que encontró la clave, pero imprime solo su longitud, nunca la clave.

## Si se hizo commit de un secreto

1. **Revoca la clave** en el sitio web del servicio de inmediato y crea una nueva. Este
   es el paso que importa. Supón que cualquiera pudo haberla copiado.
2. Elimínala de tus archivos y guárdala en `.env`.
3. Reescribir el historial es un procedimiento delicado. Pide ayuda antes de intentarlo.
   Revocar la clave es lo que te protege.

## Manos a la obra

### Ejemplo resuelto

1. Crea `.gitignore` en tu proyecto con las líneas del ejemplo.
2. Crea `.env` con un valor **falso**, como `CAFE_API_KEY=not-a-real-key`.
3. Ejecuta `git status`. El archivo `.gitignore` aparece como nuevo, pero `.env` no.
4. Haz commit de `.gitignore` con un mensaje claro.

### Ahora tú

¿Por qué añadir `.env` a `.gitignore` después de haber hecho commit de él no resolvería
el problema?

<Checkpoint question="Muestra la respuesta">
	Git ya guarda el archivo en instantáneas anteriores, y `.gitignore` solo
	afecta a los archivos que todavía no controla. La clave permanece en el
	historial, así que hay que revocarla.
</Checkpoint>

## Errores comunes

- **Añadir `.gitignore` demasiado tarde.** Créalo al principio.
- **Hacer commit de `.env.example` con una clave real.** El ejemplo debe contener un marcador de posición.
- **Pensar que un repositorio privado es seguro para los secretos.** Se añaden personas, los repositorios
  se vuelven públicos y las laptops se pierden. Mantén los secretos fuera de todos modos.
- **Escribir la clave directamente en el programa "solo por ahora".** Suele quedarse ahí.
- **Saltarte la revocación.** Borrar no es suficiente.
