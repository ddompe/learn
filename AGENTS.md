# Instructions for AI coding agents

This repository is learn.dompe.space, a multi-course tutorial site built with Astro Starlight.
The first course is `automation-ai` (Automation & AI for Business Users).
Read this file fully before making changes.

## Project context

- Audience: business professionals (Excel, PowerBI, Office users) with no programming
  background. Assume no prior knowledge of terminals, paths, or programming.
- Source language: English. Spanish translations live in a parallel tree. Never edit a
  Spanish page as part of an English content task unless the task says so.
- Planning documents live in `planning/`. The curriculum (`planning/02-curriculum.md`)
  and content guide (`planning/04-content-guide.md`) are authoritative.

## Repository layout

- `src/content/docs/<locale>/index.mdx` - course catalog
- `src/content/docs/<locale>/about.mdx` - about the author
- `src/content/docs/<locale>/<course>/` - lessons for a course (MDX)
- `src/content/docs/es/` mirrors `src/content/docs/en/`
- `src/components/` - custom MDX components shared by all courses
- `courses/<course>/course.yml` - catalog metadata
- `courses/<course>/examples/` - runnable Python examples (a uv project per course)
- `courses/<course>/examples/data/` - case-study datasets
- `courses/<course>/planning/briefs/` - chapter briefs
- `scripts/` - build helpers (example runner, translation staleness checker)
- `planning/` - site-wide design docs and ADRs

## Rules for content tasks

1. Every lesson follows `planning/templates/lesson-template.mdx`. Do not omit sections.
2. Every lesson includes a `<PromptExample>` with a good prompt, a lousy prompt, and an
   explanation of the difference.
3. Code shown in a lesson must come from a real file in `courses/<course>/examples/`, imported with
   `?raw`. Do not paste code that is not tested.
4. Every example has a pytest test, or is listed in
   the course's `examples/README.md` with a reason why it cannot be tested.
5. Expected outputs are generated by `scripts/run_examples.py`. Never hand-write output.
6. Use the Cafe Central case study for examples unless the brief says otherwise.
7. Introduce each new term in bold on first use and add it to `planning/glossary.md`.
8. Keep sentences short. Explain why before how. Use no unexplained jargon.
9. Pages with fast-changing facts (models, prices, vendors) must set `lastVerified` in
   frontmatter.

## Rules for code and infrastructure tasks

- Use `npm` for the site and `uv` for Python. Do not add pip, poetry, or conda instructions.
- Run before every commit: `npm run check` (lint, format, spell, links) and
  `uv run pytest` inside each changed `courses/<course>/examples/`.
- Do not add dependencies without noting them in the PR description.

## Definition of done

See `planning/06-implementation-plan.md#definition-of-done`. A task is not complete until
every checklist item passes.
